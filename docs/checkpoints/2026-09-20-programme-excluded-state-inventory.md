## Boundary

after genuine restricted-runtime provisioning and before foundation setup. It
compares that baseline after setup, proposals, review, items, planning, physical
approval, staffing, release, changes, on-site output, continuity and archive.

guards, fixtures or the original baseline when a difference appears.

Accreditation, Catalog, Charities, Communications and Logistics are covered.
Installed native relation identities must equal owner model metadata, not just
the familiar Participation pair. Each coherent repeatable-read snapshot runs as
the exact fixture's genuine `maru_runtime` login. PostgreSQL computes sorted SHA-256
row fingerprints without returning private rows. A fixed 10,000-row per-relation
limit, five-second statement limit and one-second lock limit fail closed on
overflow/unavailability; no partial inventory is accepted. Existing seed/catalog
rows remain part of the baseline, so updates and removals are visible too.

Every observation rejects domain-event names/versions outside the literal
candidate's v1 internal routes, non-internal outbox destinations, or persisted
grant/bundle capabilities belonging to excluded owners. This does not claim that
every allowed event payload or every role/object/field boundary has been verified.
Snapshot representations and errors exclude row contents, private identifiers and
credentials. Only the scoped launcher has the database handle; this is not a new
administrative query or export API.
